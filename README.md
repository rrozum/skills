Практические скиллы Романа Розума для работы с ИИ-агентами в разработке.

Они помогают разобраться в реализованной бэкенд-фиче, найти нужные участки кода и сохранить контекст для команды. Основной результат — документы, по которым разработчик может продолжить исследование, ревью или разбор проблемы.

Канал автора: [Rozum in the Loop](https://t.me/rozum_in_the_loop).

## Что есть в репозитории

| Скилл | Когда использовать | Что получится |
| --- | --- | --- |
| [backend-feature-architecture](skills/backend-feature-architecture/SKILL.md) | Нужно понять устройство готовой фичи и выбрать порядок чтения кода | Текстовая схема архитектуры, основные сценарии, точки входа и ссылки на реализацию |
| [backend-feature-troubleshooting](skills/backend-feature-troubleshooting/SKILL.md) | Нужно подготовить навигатор для сопровождения фичи | Таблица "Проблема — трасса — код" и пошаговые пути диагностики с условиями и развилками |

Скиллы независимы. Для навигатора проблем не обязательно сначала строить карту архитектуры.

## Для каких проектов

Для реализованных бэкенд-фич, особенно когда в них есть несколько путей выполнения, фоновые задачи, интеграции или раздельные запись и чтение данных.

В инструкциях используется обозначение `Class::method()`, привычное для PHP. Сами задачи не привязаны к фреймворку. Для другого языка просите использовать реальные имена функций, модулей и обработчиков; не нужно придумывать классы ради формата.

Агенту нужен доступ на чтение к исходникам исследуемой фичи. Полезны спецификация, тесты и существующая документация. Доступ к production, секретам и персональным данным для этих скиллов не требуется.

## Установка

1. Скачайте репозиторий и распакуйте архив.
2. Скопируйте нужные папки из `skills/` в каталог скиллов своего агента. Например, в `.agents/skills/` внутри проекта, если ваш агент использует этот путь.
3. Откройте проект с кодом фичи и используйте один из запросов ниже.

Или укажите своему агенту путь к скачанной папке и попросите:

```text
Установи backend-feature-architecture и backend-feature-troubleshooting
из папки skills/ скачанного репозитория rozum-skills в этот проект.
Используй каталог скиллов, который поддерживает твой инструмент.
```

## Примеры запросов

Указывайте конкретную фичу, ее границы и желаемое место результата. Примеры ниже описывают условную фичу экспорта отчетов и не являются результатами ее реального исследования.

### Карта архитектуры

```text
Используй $backend-feature-architecture.

Разбери реализованную фичу фонового экспорта отчетов в текущем репозитории.
В область входят создание задания через API, фоновая обработка и скачивание файла.

Покажи точки входа, основные компоненты и движение данных.
Для этого проекта используй реальные имена функций и модулей.
Отметь участки, которые нельзя подтвердить доступным кодом.
Результат верни в чат. Файлы не меняй.
```

Результат должен помочь ответить на вопросы: кто запускает обработку, где сохраняется состояние задания, как появляется файл и откуда API читает готовый результат.

### Навигатор проблем

```text
Используй $backend-feature-troubleshooting.

Подготовь навигатор возможных проблем той же фичи фонового экспорта отчетов.
Выдели основные симптомы, которые следуют из текущей реализации.
Для каждого покажи путь по коду, проверки и условия перехода дальше.

Не считай пример симптома доказательством бага.
Не обращайся к production и не повторяй операции.
Результат верни в чат. Файлы не меняй.
```

Если соответствующие механизмы найдены в коде, навигатор может объяснять, с чего начать проверку задания, которое остается в обработке, или готового файла, недоступного для скачивания. Конкретные причины и сигналы агент должен установить по реализации.

Для сохранения документа вместо ответа в чат укажите целевой путь в документации своей фичи. Сохраненный документ стоит держать рядом с кодом и обновлять после изменений затронутых сценариев.

## Развитие

Коллекция будет пополняться приемами, которые автор использует в разработке. Возможное следующее направление — маршрут ревью большой фичи: в каком порядке читать реализацию и где проверять требования.

Новые скиллы добавляются по мере реального использования. Если текущих двух достаточно, репозиторий остается небольшой коллекцией без обязательного плана расширения.

Предложения по улучшению полезнее сопровождать обезличенным запросом, описанием полученного результата и конкретным местом, которое оказалось неудобным. Не прикладывайте секреты, персональные данные или закрытый код.
